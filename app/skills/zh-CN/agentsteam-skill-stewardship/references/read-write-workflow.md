# 读取、判断与写入

## 1. 明确候选

从当前证据中确定：适用场景、有效方法或需修正的步骤、机制原因、结果依据。检查[资格与边界](eligibility.md)后再选目标。多个独立候选按顺序处理；一条完成或停止后再处理下一条。

## 2. 检查完整个人技能清单

列举个人维护源下全部 `<skill-name>/SKILL.md`，读取名称和描述，结合本轮实际加载的技能确定相关类别。扫描失败或清单不完整时，先解决读取问题；不能从索引子集推出“没有已有技能”。

按主技能的四级顺序选位置：当前已用个人技能、已有类别技能、该类别的专题文件、新类别技能。创建个人技能前检查当前 Harness 可见的全局和项目技能名称，避免新会话因重名排除它。

## 3. 本次修改前重新读取

完整读取维护源中的目标 `SKILL.md`。修改已有支持文件时，也要重新读取那个具体文件；旧对话引用、搜索片段和 runtime 快照不能替代这次对维护源的读取。

搜索目标技能及其 `references/` 中相同或近义的规则。文件搜索用于定位，判断和修改依据完整相关正文；内容缺失或目标不可读时停止该候选。

## 4. 作出一次明确决定

| 检查结果 | 决定 |
| --- | --- |
| 同一规则已完整存在，当前经验没有新条件或改进 | 停止，不写 |
| 同一规则错误、过时、条件不足或缺少关键步骤 | 修订原句或受影响的步骤 |
| 类别已覆盖，新增的是独立且有证据的方法 | 增补适用步骤；分支较长时扩展或新增专题文件 |
| 现有类别确实不覆盖，且有明确长期价值 | 新建类别级技能 |
| 证据、适用范围或目标仍不确定 | 停止或向用户确认影响结果的歧义 |

选择修订时，把经验放在实际影响的步骤旁；新建支持文件时同时添加主文件的相对指针和加载条件。每个候选作一次有意义的更新，避免为措辞润色反复改写。

## 5. 使用当前工具写入

依照当前工具列表使用文件读取、搜索、精确补丁或写入工具；只调用确实存在的接口。新建前检查目标尚不存在，修订以刚读到的正文为基础，保留无关内容。

精确补丁因内容变化被拒绝时，重新读取实际文件、重新比较候选，至多重试一次；再次冲突就停止并报告。工具没有并发版本检查能力时，只能按其实际能力操作；重读本身不提供并发原子保证。

工具权限不足或文件不可写时，保留原文件并报告未保存的原因，遵循现有权限流程。只有文件实际写入成功，才进入保存核验。

## 6. 重读与验证

重新读取全部实际修改的文件，核对：

- YAML 能被当前技能发现器读取，`name` 与技能目录一致，`description` 能触发正确类别。
- 本次规则已在对应位置生效，原有无关步骤保留，同一规则没有重复或矛盾版本。
- 主文件中的相对引用、加载条件与实际支持文件对应。
- 命令、参数、接口与配置键来自真实资料或实际验证，前提和平台限制明确。
- 新增或修改的脚本完成与变更匹配的执行验证；未覆盖部分有明确说明。

结构正确只说明文件可读，不能代替方法验证。核验失败时修正本次变更；若无法修正，如实报告文件状态和失败项，不能报告为已完成的沉淀。

## 7. 交付与后续复用

在本轮结果中简述“新增／修订 + 技能名 + 维护源路径 + 具体方法 + 实际验证”。资料支持的方法明确说明来源依据与未运行范围；有候选但未落盘时说明“未保存”与原因。

后续从索引发现技能后读取正文与所需引用。当前会话需要刚写入的经验时读取个人维护源；新会话通过既有装配加载新版本。上下文压缩造成正文缺失时重新读取。
